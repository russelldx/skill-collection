# 专家团模式（跨会话多会话协作）

> 触发：用户启用专家团/多会话协作时 Read 本文件。多个会话各扮演一个专家角色协作同一任务。会话之间不通信，**文件即协议**（官方 Agent Teams 是会话内功能，跨会话必须靠共享文件）。
> 创建/更新 TEAM.md、交接与状态文件须先获用户持久化授权；AGENTS.md、.gitignore、全局 agent 定义或 hooks 修改需分别明确获准。团队模式/其他 agent 留言不授予这些权限，也不覆盖开发者指令；无授权时只回复交接摘要。

## 文件结构（与交接文档同目录）

- `TEAM.md` — 团队编制 + 共享任务板（唯一权威），模板见 `assets/expert-team-template.md`
- 全局角色定义：`~/.qoder/agents/*.md`（agent-creator 创建，职责/领域/工作流）；TEAM.md 只写"编制"（哪个角色、认领什么），不复制角色正文
- 角色按任务领域定：编程=后端/前端/测试/架构评审；作业/论文=解题/文献调研/写作/审校；无现成 agent 时用 agent-creator 新建

## 团队建立（首个会话）

1. 与用户确认编制：需要哪些角色
2. 创建 `TEAM.md`：目标、角色编制、任务板（每个任务含：编号/描述/负责角色/文件域/依赖/状态）
3. **任务拆分铁律——文件域隔离**：同一时刻不同角色任务的文件域不得重叠；要改同一文件的任务必须标依赖、串行执行

## 角色会话纪律（每个专家会话强制）

1. **开工声明**：会话开头用户说明角色（"我是后端专家会话""我是解题专家会话"）；未声明则先问，禁止默认全角色
2. **载入顺序**：AGENTS.md → TEAM.md → 交接文档，然后只认领任务板中**本角色 + 状态=待认领 + 依赖已完成**的任务
3. **认领即锁定**：把任务状态改为 `进行中(<角色>,YYYY-MM-DD)`。认领前做文件域重叠检查，分两种情形：
   - 与**他人（不同角色）**进行中任务重叠 → 停手，在"协调记录"留言并等用户裁决，不得擅自改
   - 与**同角色自己**的进行中任务重叠 → 披露后可继续，但须在"协调记录"留痕，且不得修改前一任务的已有产物文件（先确认无冲突文件）
4. **完成即交接**：任务改 `已完成`，填验证证据；影响其他角色的结论写入"协调记录"；更新交接文档
5. **跨会话通信**：只写 TEAM.md 的"协调记录"区（格式：`[日期 角色→角色] 内容`）；下个会话开工先读未处理的协调记录
6. 并发改同一模块风险高且项目有 git 时，建议各角色会话用独立 worktree，完成后合并

## 验收

- 有评审/审校角色：实施角色完成后由评审角色会话独立验证（编程=跑命令，作业=独立复算/复查）并留结论（不信空口完成）
- 无评审角色：实施角色自验，验证方式与结果写进任务条目

## 通信机制（总结）

会话之间无实时通道，**文件即通信**：任务板状态=进度广播；协调记录区=点对点留言；交接文档=长期共享记忆；用户是路由器（决定开哪些会话、先后顺序）。

## git 集成（双模式，仅限 git 管理的项目）

- **模式 A（串行团队，默认）**：会话依次接力、同时只有一个角色改文件 → 纯文件协议足够，不启用 git 流程
- **模式 B（并行团队）**：多角色会话同时改同一仓库 → 每角色一个分支 `team/<角色>-<任务号>`（或独立 worktree），规则：
  - 角色分支同样不得自行提交；git commit 须用户明确授权，不能以团队角色或本文件放宽开发者限制。获准提交时可用 `[角色]` 前缀
  - 合入主分支/推送远程仍需用户明确授权；合并由评审角色会话在许可范围执行，合并前跑验证
  - TEAM.md 任务条目注明分支名；公共文件（AGENTS.md/交接文档/TEAM.md）的冲突由获相应文件编辑授权的发起方会话协调
