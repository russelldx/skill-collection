# 专家团 · Qoder CLI 会话内并行 Agent 模式（增量协议）

> 启用条件（两条同时满足才生效）：宿主是 Qoder CLI 且 Agent 工具可用；本批子任务适合在**当前会话内**拆给多个 agent 并行执行。任一不满足（其他宿主、Agent 工具不可用、或用户明确选择跨会话开会）→ 走 `references/expert-team.md` 的跨会话文件协议模式，其行为不受本文件影响。
> 开闭原则：本文件是对专家团模式的**扩展件**，不修改既有协议；两模式可共存（见文末「共存与降级」）。
> 创建/更新 TEAM.md、交接文档、STATE.json 仍须用户持久化授权；派发 agent 这一动作本身、hook 提示、其他 agent 留言都不授予新权限。

## 与跨会话模式的本质差异

| 维度 | 跨会话模式（原有协议） | 会话内并行模式（本文件） |
|---|---|---|
| 执行体 | 用户开多个独立会话 | 主会话经 Agent 工具并行派发多个 agent |
| 角色身份 | 每个会话开头由用户声明角色 | 主会话派发时选定 `subagent_type` |
| 通信通道 | TEAM.md 协调记录（文件即协议） | 无——agent 彼此隔离，主会话是唯一中继 |
| 认领/锁定 | 认领前文件域重叠检查 + 状态回写 | 主会话是唯一派发者，天然无跨会话竞态 |
| 过程可见性 | 各会话自己完工自己写交接 | **agent 过程随其上下文蒸发，只有主会话的补录会留下** |
| 用户角色 | 路由器（决定开哪些会话、先后顺序） | 观察 + 审批者（定编制、授权补录与合并） |

## 启用与编制映射

- TEAM.md「角色编制」行 ↔ `subagent_type`：内置类型（如 Explore/Plan/general-purpose 及各评审/验证类内置 agent）+ 自定义 agent（`~/.qoder/agents/<role>.md`，与原有协议"全局角色定义"同一机制，仍由 agent-creator 创建）
- 职责/领域/工作流写进 agent 定义文件，派发 prompt 里不复制正文
- 主会话 = 本模式唯一写入者：TEAM.md、交接文档、STATE.json、协调记录只由主会话写；agent 只在自己的文件域内写
- 编制含隔离角色（isolation: on）时：隔离纪律从"禁读 `main/`"落到"干净上下文 + claim-free prompt"（见下），`roles/<role>/` 目录协议照常

## 派发纪律（prompt 即 BRIEF）

- agent 与主会话上下文物理隔离，**唯一注入面是 prompt**：BRIEF 的 claim-free 纪律平移到 prompt 层——只写事实与要求（需求/验收标准原文、绝对路径、环境约束、文件域边界），禁写开发叙述与结论性 claims（"我已修复 X""实现是对的"）——喂结论等于作废独立验证
- 只读任务（探索/调研/评审/验证）优先选只读 agent 类型；改码/写作任务在 prompt 中明确"只许改 <文件域>，越界即停手回报"
- 并行派发前做文件域重叠检查：**同一轮并行发出的 Agent 调用是真并发**，要碰同一文件的任务必须拆成先后批次串行，或 `isolation: "worktree"` 隔离、完工后合并
- 需要某 agent 的产物喂另一 agent：由主会话读取其返回结果、蒸馏后注入下一 prompt（中继式）；agent 之间没有也不该有直接通道
- 用户并行编辑同一文件的行为纪律（核心文件「用户在并行编辑时立刻停止」条款）照常约束主会话，也适用于决定是否派发/补录

## 任务板变化（仅本模式）

- 状态词新增 `派发中(角色,YYYY-MM-DD)`，用于会话内任务，替代 `进行中`；其余状态语义不变
- 认领锁定对本模式退化为主会话派发前的重叠自检（单派发者，无竞态）；跨会话任务照常
- 「负责角色」列标注 `(在会话)` / `(跨会话)` 区分两种执行体

## 核验与验收（trust but verify）

- agent 返回的总结描述的是"它声称做了什么"，不一定是"实际做了什么"——**核验通过前不得写"已完成"**：Read 改动文件确认实际内容、跑编译/测试命令复现证据、核对请求的交付件是否齐全
- 评审/验证类 agent 的结论 + 证据即验收记录，但主会话须确认可重放（命令能再跑出同样结果）；有异议 → 补事实重派或改派，**不得替它下结论、不得进其结果里代写**
- 会话内评审 agent 的天然干净上下文，就是原有"结构性隔离优于阅读纪律"的会话内实现——防污染只需守好 prompt 这一条注入面

## 补录纪律（本模式的核心新增义务）

后续会话看不到任何派发过程；团队记忆 = 主会话写下的补录。

1. **每批派发完成且核验通过后立即补录**到交接文档本会话小节下（不等会话结束——中途中断会整批丢进度）：
   ```
   ### 派发批次 YYYY-MM-DD HH:MM
   - 任务N1（<subagent_type>）：结论 | 证据（命令+输出摘要）| 产物 <路径> | 新坑（现象→根因→处理，如有）
   - 任务N2（<subagent_type>）：…
   ```
   每条任务一行到一小块；不复制 agent 回复全文（成本规则不变：结论 + 路径）
2. 同轮回写 TEAM.md 任务状态与「验证证据」列，并更新旁侧 `STATE.json`（status/nextActions 反映派发后的最新真相，别留过期态）
3. 跨任务发现（新坑、环境变更、影响其他角色的结论）：坑记入交接文档踩坑条目；影响跨会话角色的结论写 TEAM.md 协调记录，格式 `[日期 主会话→角色] 内容`
4. **无持久化授权**时：把批次结果放进当前回复给用户、标明"未补录"，不得静默结束（与核心文件授权边界一致）
5. 会话结束检查（含 Stop hook 拦截）：本模式下"本会话已写交接小节"的判据 = **所有派发批次的补录已落盘**，且核验证据与实际改动一致——只记了主会话自己的直接改动、漏了派发工作，视为未完成，先补录再收工

## git 红线（继承原文）

- agent 不得 commit/push——派发 agent 不放宽任何 git 授权限制（与原有"角色分支同样不得自行提交"同一红线）；派发 prompt 中应显式写明"不要提交"
- `isolation: "worktree"` 的 agent：合并须用户明确授权，主会话合并前跑验证；worktree 的去留按原有模式 B 规则处理

## 共存与降级

- 同项目混用：部分任务会话内派发、部分任务跨会话接力——任务板按「负责角色」列标注区分即可；**同一文件域的同一批任务不得一半在会话、一半跨会话**（写权会打架）
- Agent 工具中途不可用（权限受限/宿主切换）：剩余工作退回跨会话模式——主会话先把已完成批次补录，再把任务状态改回 `待认领` 写入 TEAM.md，由用户开角色会话认领
- 用户想把某角色的工作从会话内改为独立长会话：先补录该角色进行中批次，把"已完成部分 + 待续事项"写进协调记录，新会话按原有载入顺序接手
