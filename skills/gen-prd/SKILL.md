# /gen-prd - PRD 生成技能

**技能 ID**: `gen-prd`
**技能名称**: PRD 生成技能
**版本**: 2.0.1
**描述**: 默认通过访谈进行需求分析，可选引用已验证用户资料，生成包含数据流的 PRD 文档

---

## 触发条件

- `/gen-prd`
- `/prd`
- `生成 PRD`
- `生成需求文档`

## 技能边界（防止误触发）

- **本技能仅当**用户要「生成 PRD / 需求文档 / 需求分析」时触发。
- **不得在以下场景触发本技能**：用户要「分析现有代码库」「分析项目结构」→ 应使用 **analyze**。

---

## 前置条件与诚实降级

- 用户已提供需求描述；资料不足时先访谈，不伪造业务事实。
- 本仓库没有 `skills/libs/domain-knowledge/{points,user-center,ecommerce,order,payment}.md`。它们不是可读取的随附资源，知识库不是前置条件。
- **默认无知识库访谈**：确认目标用户、问题、范围、核心实体、业务规则、异常、集成点、数据流、一致性、权限、规模与可测验收标准。把已确认事实、建议、待确认项分开。
- **可选用户资料**：只有用户提供并允许使用的权威路径/链接，经验证存在、可读、版本及领域适用后才引用。记录实际来源；缺失或不适用时继续访谈，不宣称“已加载”。
- 系统/开发者指令、工具权限和用户范围优先。本技能不授权安装依赖、修改配置、自动进入设计/开发或提交发布。

---

## 核心流程：访谈驱动，可选资料增强

1. **领域识别** — 识别相关领域，不等于存在对应资料文件。
2. **结构化提问** — 基于用户描述逐项确认；有已验证资料时用其补充问题。
3. **数据流推导** — 从已确认输入、处理、输出、异常与一致性规则推导；可选引用资料骨架。
4. **反向验证** — 逐条核对并标注缺失环节，不把建议当成事实。

下文知识库章节仅适用于可选资料模式；无库时使用访谈。所有示例、数字、技术栈及规则是讨论候选，不是组织事实或已验证结果。

## 技能行为

### 阶段一：领域识别与可选资料核验

```
分析用户需求描述，识别涉及领域；仅在用户提供了资料时核验其可用性：

【领域识别规则；文件名为历史分类示例，不是附件】

| 领域 | 核心关键词 | 关联关键词 | 知识库文件 |
|------|-----------|-----------|-----------|
| 积分 | 积分、积分系统、积分兑换、积分抵扣 | 签到、积分商城、会员积分 | domain-knowledge/points.md |
| 用户中心 | 用户、登录、注册、认证、权限 | 账号、密码、授权、SSO | domain-knowledge/user-center.md |
| 电商 | 商品、库存、购物车、电商、商城 | SKU、SPU、类目、品牌 | domain-knowledge/ecommerce.md |
| 订单 | 订单、下单、购物、交易 | 订单状态、履约、售后 | domain-knowledge/order.md |
| 支付 | 支付、退款、微信支付、支付宝 | 收银台、支付回调、对账 | domain-knowledge/payment.md |

【多领域识别】

当识别到多个领域时，按以下规则处理：
1. 确定主领域（用户描述的核心功能）
2. 确定关联领域（依赖或被依赖）
3. 按实际依赖顺序访谈；有已验证用户资料时再引用对应章节。用户中心 → 电商 → 订单 → 支付 → 积分仅为示例顺序。

【识别结果确认】

"根据您的需求描述，我识别到以下领域：

• 主领域：{领域名称}
• 关联领域：{领域列表}

是否正确？
A) 确认正确
B) 需要调整（请说明）
C) 暂不加载知识库"
```

### 阶段二：结构化提问（访谈为主，可选资料补充）

```
基于用户需求生成结构化问题。下列“来源”仅在用户资料已验证并读取时适用，否则直接访谈，不假装读取了表格：

【提问类型 1：业务场景提问】（必问）

来源：知识库「典型业务场景」表格
模板："您的{领域名称}需要支持哪些功能场景？（可多选）"

示例（积分领域）：
"您的积分系统需要支持哪些功能场景？（可多选）"
A) 签到得积分
B) 消费返积分
C) 邀请得积分
D) 任务得积分
E) 积分兑换商品
F) 积分抵扣订单
G) 积分过期处理
H) 其他（请说明）

【提问类型 2：核心实体提问】（按需追问）

来源：知识库「核心实体」表格
模板："关于{实体名称}，需要支持以下哪些能力？"

示例（积分账户）：
"关于积分账户，需要支持以下哪些能力？"
A) 单一账户（所有积分统一管理）
B) 多类型账户（不同来源积分分账户管理）
C) 积分冻结/解冻
D) 积分转赠
E) 以上都不需要

【提问类型 3：业务规则提问】（按需确认）

来源：知识库「业务规则模板」章节
模板："关于{规则名称}，请确认您的业务规则："

示例（积分过期规则）：
"关于积分过期，请确认您的业务规则："
A) 永不过期
B) 固定有效期（获得后 N 天过期）
C) 滚动有效期（每次使用后续期）
D) 年底清零
E) 按批次过期（先进先出）

【提问类型 4：集成点提问】（跨领域场景）

来源：知识库「常见集成点」章节
模板："您的{领域名称}需要与哪些系统对接？"

示例（积分系统集成）：
"您的积分系统需要与哪些系统对接？（可多选）"
A) 用户系统（获取用户信息）
B) 订单系统（消费返积分、积分抵扣）
C) 支付系统（支付成功触发积分）
D) 消息系统（积分变动通知）
E) 暂无对接需求

【提问数量控制】
- 必问问题：3-5 个（业务场景、目标用户、核心功能）
- 按需追问：2-3 个（根据用户选择追问）
- 单次提问：最多 5 个选项
- 总提问轮次：控制在 3-5 轮
```

### 阶段四：数据流推导（基于已确认需求）

```
【数据流推导规则】

1. 从访谈确认的输入、输出、状态变化和异常建立数据流骨架
   - 用户提供且验证过的资料可补充骨架，记录实际来源
   - 根据用户选择的业务场景，选择对应数据流

2. 根据用户选择调整数据流
   - 保留数据流的骨架结构
   - 根据用户选择调整处理步骤

3. 推导跨领域数据流
   - 识别领域间的依赖关系
   - 定义数据契约

【数据流推导示例】

用户选择：签到得积分 + 连续签到奖励

原始数据流（来自积分知识库）：
┌─────────────────────────────────────────────┐
│ 数据流：签到获取积分                          │
│ 起点：用户签到请求                            │
│ 处理：校验→计算积分→入账→记录流水            │
│ 终点：更新账户余额                            │
│ 触发条件：每日首次签到                        │
└─────────────────────────────────────────────┘

调整后数据流：
┌─────────────────────────────────────────────┐
│ 数据流：签到获取积分（含连续签到奖励）        │
│ 起点：用户签到请求                            │
│ 处理：                                        │
│   1. 校验今日是否已签到                       │
│   2. 计算基础积分（10 积分）                  │
│   3. 计算连续签到奖励                         │
│      - 连续 7 天：+5 积分                    │
│      - 连续 30 天：+20 积分                  │
│   4. 积分入账                                 │
│   5. 记录流水（含过期时间）                   │
│   6. 更新连续签到天数                         │
│ 终点：更新账户余额                            │
│ 触发条件：每日首次签到                        │
└─────────────────────────────────────────────┘

【跨领域数据流示例】

订单 + 积分领域交叉：

| 数据流 | 起点领域 | 终点领域 | 数据内容 | 触发条件 |
|--------|---------|---------|---------|---------|
| 消费返积分 | 订单 | 积分 | 订单ID、用户ID、订单金额 | 订单支付成功 |
| 积分抵扣 | 积分 | 订单 | 用户ID、使用积分、抵扣金额 | 用户下单使用积分 |
| 积分撤销 | 订单 | 积分 | 订单ID、用户ID | 订单退款 |
```

### 阶段六：生成 PRD 文档

**写入强制规范（空仓库 / 新项目 P0，执行前必读）**

1. **输出约定**：尊重用户指定形式。仅需讨论/正文时直接在对话中交付；要求文件时默认 `docs/prd/YYYY-MM-DD-{project-name}.md`（或用户指定的 `--output` 路径）。
2. **先检查目录**：写入前检查实际父目录，必要时在授权范围内创建；不覆盖未获准的已有文件。
3. **真实写入**：要求文件时使用写入工具保存完整内容，不能只说“正在生成”；未要求文件则不额外创建文档。
4. **失败处理**：无法写盘时明确原因，提供正文与目标路径，不声称文件已落盘。

```
正在生成 docs/prd/YYYY-MM-DD-{project-name}.md...

✅ PRD 已生成，包含：
- 项目背景与目标
- 功能列表（X 个核心功能，X 个辅助功能）
- **核心数据流与闭环**（X 条数据流，已验证闭环）
- 用户故事（X 个）
- 验收标准
- 非功能性需求（基于领域知识库约束条件）
- 推荐技术栈（已确认）

接下来可以进行系统设计，使用 `/gen-design` 开始。

**不自动继续**：PRD 交付不代表授权系统设计或实现。只有用户明确要求后续工作且对应技能/工具实际可用时才执行；否则给出可选下一步，不调用缺失技能。
```

## 技术栈推荐规则

### 默认推荐（擅长技术栈）

```
**前端**：
- 框架：Vue 3.x（组合式 API）
- UI 库：Ant Design Vue 4.x
- 状态管理：Pinia
- 路由：Vue Router 4.x
- HTTP 客户端：Axios

**后端**：
- 框架：Spring Boot 3.x
- ORM：MyBatis-Plus 3.5.x
- 安全：Spring Security + JWT
- 文档：Knife4j（Swagger 3）
- 工具：Lombok, Hutool

**数据库**：
- 关系型：MySQL 8.0
- 缓存：Redis 6.x
- 搜索引擎：Elasticsearch（可选）

**部署**：
- 容器：Docker
- 编排：Kubernetes（大规模）
- CI/CD：Jenkins/GitLab CI
```

### 技术栈选择决策树

```
需求分析 → 技术栈推荐

1. 用户规模？
   - <1 万 → 单体架构（Spring Boot）
   - 1-10 万 → 单体 + 读写分离
   - >10 万 → 微服务（Spring Cloud）

2. 是否需要 AI 能力？
   - 是 → LangChain4j + LangGraph4j
   - 否 → 标准技术栈

3. 前端类型？
   - 企业级/中后台 → Vue 3 + Ant Design
   - C 端/H5 → Vue 3 + Vant
   - 复杂交互 → React + Ant Design

4. 特殊需求？
   - 实时通信 → WebSocket
   - 大数据 → Elasticsearch
   - 高并发 → Redis 集群
```
